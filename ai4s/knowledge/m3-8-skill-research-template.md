# Skill研究方案模板

> **引入时机**：W5 | **核心挑战**："如何用Skill快速生成研究方案框架？" | **层级**：Essential

## 为什么要在项目阶段学习这个知识点？

W4结束时你需要输出一份结构化的研究方案。从研究问题、理论框架、方法选择到变量设计，这些内容分散在多轮对话和多个文档中。如果每次写研究方案都从头开始，不仅效率低，而且容易遗漏关键要素。

Skill是opencode中的可复用AI能力模块——你可以把"生成研究方案"这个能力封装为一个Skill，以后每次只需要输入研究问题，就能快速获得结构化的方案框架。这不是让AI替你做研究设计，而是让AI帮你把分散的研究设计要素组织成一份完整的方案初稿，你再在此基础上修改和完善。

本知识点教你理解Skill的概念、设计研究方案Skill、编写Skill模板，并掌握Skill的复用与迭代方法。掌握这套方法后，你可以将科研中的任何重复性AI工作流封装为Skill。

## 这个知识点的核心内容

### 一、Skill概念详解

#### 什么是Skill

Skill是opencode中的可复用AI能力模块。它封装了特定任务的Prompt逻辑、执行步骤和输出格式，使得复杂的AI工作流可以被一键触发。

```
Skill vs Prompt vs Agent 的区别：

Prompt：
  - 单次输入，单次输出
  - 无状态，不记忆上下文
  - 适合简单、一次性的任务
  - 例："帮我润色这段文字"

Agent：
  - 多轮对话，有状态记忆
  - 可以调用工具（搜索、代码执行等）
  - 适合需要交互和工具使用的复杂任务
  - 例："帮我做文献综述"（需要搜索+整理+生成）

Skill：
  - 预定义的多步骤工作流
  - 有固定的输入输出格式
  - 可复用，一次编写多次使用
  - 适合结构化的重复性任务
  - 例："根据研究问题生成研究方案框架"
```

#### Skill的核心要素

```
一个Skill包含：

1. 触发条件（Trigger）
   - 什么时候激活这个Skill
   - 例：用户说"生成研究方案"或"research design"

2. 输入定义（Input）
   - Skill需要什么输入
   - 例：研究问题、学科领域、约束条件

3. 执行步骤（Steps）
   - Skill的内部工作流
   - 例：理解问题→匹配方法→设计方案→评估方案

4. 输出格式（Output）
   - Skill的输出结构
   - 例：Markdown格式的结构化研究方案

5. 约束规则（Constraints）
   - Skill的行为边界
   - 例：不做最终决策、不编造文献
```

### 二、研究方案Skill的设计

#### 输入设计

研究方案Skill需要的输入是研究问题的结构化描述：

```
输入字段：

必填：
  - research_question: 核心研究问题（一句话）
  - discipline: 学科领域（经济学/社会学/政治学/管理学/传播学）
  - research_context: 研究情境（国家、时间、层级等）

选填：
  - theoretical_framework: 已选定的理论框架（如有）
  - data_available: 已有或可获得的数据（如有）
  - method_preference: 方法偏好（如有）
  - constraints: 约束条件（时间、技能等）
```

#### 执行步骤设计

```
Step 1: 问题分析
  输入：research_question + discipline
  处理：
    - 判断问题类型（描述性/解释性/探索性）
    - 识别因果层级（关联/机制/效应）
    - 提取核心变量（自变量、因变量、调节/中介变量）
  输出：问题分析摘要

Step 2: 理论框架推荐
  输入：问题分析摘要 + discipline
  处理：
    - 推荐适配的理论框架（2-3个）
    - 对每个框架说明适配理由和局限
  输出：理论框架推荐列表

Step 3: 方法匹配
  输入：问题分析摘要 + research_context + data_available
  处理：
    - 推荐适配的研究方法（2-3种）
    - 对每种方法说明假设、数据需求、局限
    - 给出优先推荐
  输出：方法推荐列表

Step 4: 变量设计
  输入：问题分析摘要 + 理论框架 + 方法
  处理：
    - 设计核心变量的操作化方案
    - 列出控制变量
    - 标注数据来源
  输出：变量设计表

Step 5: 方案评估
  输入：完整方案草案
  处理：
    - 评估假设合理性
    - 识别设计漏洞
    - 提出修正建议
  输出：评估报告

Step 6: 方案整合
  输入：以上所有步骤的输出
  处理：
    - 整合为结构化研究方案
    - 标注需要人类判断的关键决策点
  输出：结构化研究方案（Markdown格式）
```

#### 输出格式设计

```markdown
# 研究方案：[研究问题]

## 一、研究问题

### 核心问题
[一句话陈述]

[描述性/解释性/探索性]

## 二、理论框架

## 四、变量设计

| 变量 | 类型 | 测量方式 | 数据来源 |
|---|---|---|---|
```

### 三、Skill模板编写方法

#### 在opencode中编写Skill

opencode的Skill使用Markdown格式编写，放在`.opencode/skills/`目录下：

```markdown
---
name: research-design-template
description: 根据研究问题生成结构化研究方案框架
triggers:
  - 生成研究方案
  - research design
  - 研究方案模板
---

# 研究方案模板生成Skill

## 角色设定

你是一名社科研究设计顾问，擅长帮助博士生从研究问题出发，
构建完整的结构化研究方案。你遵循以下原则：

1. 研究问题驱动方法选择，而非反过来
2. 不回避方法论局限，诚实讨论
3. 每个推荐都需要给出理由
4. 关键决策点标注为"需要人类判断"
5. 不编造文献，推荐的理论和方法需要是真实存在的

## 执行步骤

### Step 1: 问题分析

请用户输入以下信息：
- 核心研究问题（必填）
- 学科领域（必填）
- 研究情境（国家、时间、层级等，选填）
- 已有数据（选填）
- 约束条件（选填）

基于输入，分析：
1. 问题类型
2. 因果层级
3. 核心变量

输出问题分析摘要。

### Step 2: 理论框架推荐

基于问题分析，推荐2-3个适配的理论框架。
对每个框架说明：
- 核心命题
- 与研究问题的适配理由
- 潜在局限

### Step 3: 方法匹配

基于问题分析和研究情境，推荐2-3种研究方法。
对每种方法说明：
- 核心假设
- 数据需求
- 在当前情境下的适用性
- 主要局限

### Step 4: 变量设计

基于理论框架和方法选择，设计核心变量：
- 操作化方案
- 测量方式
- 数据来源

### Step 5: 方案评估

评估完整方案：
- 优势
- 风险与应对
- 需要人类判断的决策点

### Step 6: 方案整合

将以上输出整合为结构化研究方案（Markdown格式）。
标注所有需要人类判断的决策点。

## 输出格式

按照以下结构输出：

# 研究方案：[研究问题]

## 一、研究问题
## 二、理论框架
## 三、研究方法
## 四、变量设计
## 五、方案评估

## 约束

- 不编造文献引用
- 不替用户做最终方法决策
- 标注每个推荐的理由
- 标注所有需要人类判断的决策点
```

#### 在cursor/trae中编写类似工作流

如果你使用cursor或trae，可以用Composer或Rules实现类似功能：

```
在.cursor/rules/中创建research-design.md：

---

---

当用户要求生成研究方案时，按以下步骤执行：

1. 收集信息：研究问题、学科、情境、约束
2. 分析问题类型和因果层级
3. 推荐理论框架（2-3个）
4. 推荐研究方法（2-3种）
5. 设计变量操作化方案
6. 评估方案风险
7. 整合为结构化输出

原则：
- 方法选择由研究问题驱动
- 不编造文献
- 标注需要人类判断的决策点
```

### 四、Skill的复用与迭代

#### 复用场景

```
场景1：新研究项目
  你开始一个新研究，只需输入新的研究问题，
  Skill自动生成方案框架，节省2-3小时的结构化写作时间

场景2：方案修订
  导师要求调整方法，重新运行Skill，输入新的约束条件，
  快速生成修订版方案

场景3：多方案比较
  用同一研究问题但不同约束条件，生成多个方案进行对比

场景4：团队协作
  分享Skill给课题组成员，确保研究方案的结构一致性
```

#### 迭代优化

```
迭代1（V1）：基础版
  - 输入：研究问题
  - 输出：基础方案框架
  - 问题：推荐过于泛化

迭代2（V2）：增加学科特化
  - 增加学科领域的特定理论和方法库
  - 输出更有针对性的推荐
  - 问题：未考虑数据约束

迭代3（V3）：增加约束条件
  - 输入增加数据可得性、时间约束
  - 推荐方案考虑可行性
  - 问题：评估不够严格

迭代4（V4）：增加方案评估
  - 增加压力测试和审稿人视角评估
  - 输出包含风险评估和应对策略
  - 问题：输出格式不稳定

迭代5（V5）：固定输出格式
  - 严格定义输出Markdown结构
  - 确保每次输出格式一致
```

#### 版本管理

```
建议将Skill纳入git版本管理：

.opencode/skills/
  research-design-v1.md     （基础版）
  research-design-v2.md     （学科特化版）
  research-design-v3.md     （当前使用版）

每次迭代保留旧版本，方便回退和对比。
在SKILL.md中注明当前推荐版本和变更记录。
```

## 关键细节与易错点

- **易错：Skill输出当最终答案**。Skill生成的是方案初稿，你需要审核每个推荐、验证每个假设、补充学科特异性的细节。直接提交Skill输出是研究设计不负责任的表现
- **易错：Skill不迭代**。第一次编写的Skill一定不够好，需要根据使用反馈持续迭代。如果Skill推荐的方法总是不适合你的领域，说明需要增加学科特化逻辑
- **易错：Skill过于通用**。试图写一个"万能研究方案Skill"，结果对任何学科都不够深入。更好的策略是为自己的学科写特化版本
- **易错：忽略Skill的约束规则**。如果不设约束，Skill可能编造文献、替你做决策、回避局限。约束规则是Skill质量的保障
- **易错：把Skill和Prompt混淆**。Skill是多步骤的结构化工作流，不是单个Prompt。如果只需要一句话就能完成的任务，不需要封装为Skill
- **易错：不记录Skill的使用反馈**。每次使用Skill后，记录"推荐了什么、采纳了什么、修改了什么"，这些反馈是迭代优化的依据

## 社科科研示例

你是经济学博士生，研究"房产税试点对居民消费的影响"。

**使用Skill的过程**：

```
输入：
  research_question: "房产税试点是否降低了试点城市居民的消费水平？"
  discipline: "经济学"
  research_context: "中国，2011年起沪渝房产税试点，省级面板数据"
  data_available: "省级面板数据2010-2020，包含消费、收入、房价等"
  constraints: "8周完成，熟悉DID和面板回归"

Skill输出（关键部分）：

## 研究问题
- 类型：解释性（因果效应估计）
- 因果层级：效应（X对Y的因果效应有多大）
- 核心变量：自变量=房产税试点，因变量=居民消费水平

## 理论框架
推荐1：税收负担理论——房产税增加居民税负，挤占可支配收入
推荐2：财富效应理论——房产税影响房价预期，通过财富效应影响消费
建议：以税收负担理论为核心，财富效应理论作为补充机制

## 研究方法
推荐1：DID——沪渝试点vs非试点，有政策前后数据
  假设：平行趋势（需检验：2011年前试点与非试点消费趋势是否一致）
  风险：只有2个试点城市，处理组样本量小
推荐2：SCM——为上海/重庆分别构建合成控制组
  优势：更适合处理组样本量小的场景
建议：DID为主（与现有文献可比），SCM做稳健性检验

## 需要人类判断
- [ ] 平行趋势是否成立（需要你自己检验数据）
- [ ] 是否控制房价（可能是中介变量而非控制变量）
- [ ] 沪渝两个城市是否应分开分析（异质性问题）
```

**你的后续工作**：
1. 检验平行趋势（发现2010年前趋势基本一致，假设成立）
2. 思考房价的角色（决定不控制房价，因为它是中介变量）
3. 决定沪渝分开分析（两个城市的税制设计不同）

**Skill迭代记录**：V1版未提示"房价可能是中介变量"的问题，在V2中增加"识别潜在中介变量vs控制变量"的步骤。
