## 步骤 1 | 提取 JSON（10 分钟）

大模型输出是长文本，程序化消费它的第一步是抠出 JSON：

```python
import re, json

def extract_json(response):
    match = re.search(r"\{.*\}", response, re.DOTALL)
    if not match:
        raise ValueError("未在响应中找到 JSON 数据")
    return json.loads(match.group())

prediction = extract_json(answer)
```

**🔍 逐行拆解**：

| 代码 | 在做什么 |
|---|---|
| `re.search(r"\{.*\}", response, re.DOTALL)` | 正则找"第一个 `{` 到最后一个 `}`"的片段——JSON 长什么样就抠什么 |
| `re.DOTALL` | 让 `.` 也匹配换行——JSON 通常是多行的，没它只抠到第一行 |
| `json.loads(...)` | JSON 字符串 → Python 字典（`{"up": 0.35}` → `{'up': 0.35}`） |
| `raise ValueError` | 抠不到就明确报错，**别让下游拿着 None 崩得更远** |

**显示到页面上**——从这一刻起，概率是"数据"了，给它产品级的出场方式（指标卡，基础篇第 1 节步骤 6 讲过）：

```python
st.subheader("预测概率")
st.metric("上涨概率 (up)", f"{prediction['up']:.1%}")     # key 是 up——基础篇 2.4 在 prompt 里定下的契约
st.metric("下跌概率 (down)", f"{prediction['down']:.1%}")
```

👀 **观察**：页面上并排两张指标卡，`0.35` 变成了 **35.0%**——比 `print` 的 `{'up': 0.35, 'down': 0.65}` 直观得多。

💣 **常见坑**：`KeyError: 'up'` → 模型没按契约输出（key 可能是"上涨/downward"等）。两道防线：① 检查 prompt 输出规范里的 `with keys: up and down` 是否抄全；② 取值改用 `prediction.get("up", 0)`（取不到给默认 0，不崩页面）。**契约在 prompt，兜底在代码**——两道都要有。

✅ **检查**：`{prediction['up']:.1%}` 里的 `:.1%}` 是什么？
答：f-string 格式化——小数转百分比、保留 1 位小数（`0.35` → `35.0%`）。和基础篇的 `:+.2f`（强制正负号）是同一门手艺：**数值在给用户看之前，先想好以什么面目出现**。

**追问自己**：为什么不直接信大模型的输出格式？——因为它输出的是自然语言，格式不保证，所以要用正则兜底提取 + try/except。

## 步骤 2 | 先手写骨架（15 分钟）★架构师的工作

**骨架必须自己写**——这是你给 AI 的图纸，也是你在整个 APP 里"真正拥有"的部分。骨架想清楚了，AI 才填得对：

```python
with st.sidebar:                                        # ① 侧栏：放选择和触发
    selected = st.selectbox("选择股票", stock_options)
    code, name = selected.split()
    if st.button("🔮 开始预测", type="primary"):       # ② 按钮：用户主动触发
        df = fetch_daily_basic(code, days=5)           # ③ 取数（基础篇 2.2 的循环，包成函数）
        with st.spinner("AI 正在分析（约 10-30 秒）…"): # ④ 等待反馈（不是死寂）
            answer = llm_chat(build_prompt(name, df))  # ⑤ 预测（基础篇 2.3/2.4）
        prediction = extract_json(answer)              # ⑥ 提取（步骤 1）
        st.metric("上涨概率", f"{prediction['up']:.1%}")
        st.metric("下跌概率", f"{prediction['down']:.1%}")
        with st.expander("展开 AI 完整分析"):           # ⑦ 过程折叠，结论突出
            st.markdown(answer)
```

**骨架设计的四个决定**（每个都问自己"为什么"）：

1. **为什么用按钮触发，而不是选完股票自动预测？**——每次预测要 10-30 秒 + 花 API 钱；用户换着玩下拉列表时会触发一连串预测。**贵的操作让用户主动触发**（这就是步骤 1-5 节 rerun 机制的延续：rerun 不等于重算，`if st.button` 就是那道闸门）
2. **为什么取数包成函数 `fetch_daily_basic(code)`？**——基础篇 2.2 的循环代码要在按钮回调里复用；包成函数才能"传参换股票"
3. **为什么 spinner 而不是进度条？**——单次 API 调用不知道进度百分比（基础篇加餐讲过选型）
4. **为什么 expander 折叠完整分析？**——用户先看结论（概率），想深究再展开过程；**信息层级 = 产品思维**

✅ **检查**：这 20 行里，哪几行是你基础篇写过的、哪几行是新的？
答：③⑤⑥ 全是旧零件；新东西只有编排（侧栏、按钮、spinner、expander）。**产品 = 旧零件 × 新编排**。

## 步骤 3 | 把零件交给 AI 组装（30-40 分钟）★你当架构师

把**三样东西**一起作为上下文交给 Cursor/OpenCode：

1. 基础篇跑通的函数代码（`fetch_daily_basic`、`llm_chat`、`build_prompt`、`extract_json`）
2. 上面的骨架
3. 一句需求描述

提示词模板（按你的实际情况改写）：

> "这是我的取数函数、llm_chat、build_prompt、extract_json（粘贴代码），这是我要的界面骨架（粘贴）。请组装成完整的 app.py：侧栏 selectbox 选股票（预设列表我已给），点按钮触发预测，st.spinner 显示等待，主区域展示数据表、涨跌概率（metric 或条形图）、AI 分析过程（expander）。**保留我的函数不动，只写 UI 编排**。"

**提示词的三个要件**（和基础篇环境准备的 AI 热身同款结构）：

- **给上下文**：粘贴你的零件代码——AI 不用猜、不会发明不存在的函数
- **给骨架**：粘贴你写的编排——架构决定权在你
- **给约束**："保留我的函数不动"——这就是契约（和 2.4 的 `with keys: up and down` 同一思想：**把不可协商的部分写死**）

📎 建议流程：先让 AI 出完整版 → 跑一遍 → **只提一处最要紧的修改**再让 AI 改 → 再跑。小步迭代胜过一次提十个要求。

## 步骤 4 | 验收 AI 的产出（15 分钟）★评分点所在

跑起来后逐项核对：

- [ ] 换一只股票再点按钮，数据和结论跟着变（不是只有第一次的缓存结果）
- [ ] 按钮没点时页面不报错（给个 `st.info("👈 请先选择股票")` 之类的引导）
- [ ] `extract_json` 失败时页面不崩（try/except + 把原始回复展示出来）
- [ ] **找出 AI 代码里你必须手改的 1-2 处**（通常是：token/`.env` 读取方式、列名与你的 df 不一致、硬编码的股票列表）——**记入自查留档，这是本实验的检查重点**

**✅ 过关验收（对照成品）**：功能与 `weeks/week07/cases/app.py` 一致；你的版本能换股票、能复跑、失败不崩。

💣 **常见坑**：`json.decoder.JSONError` → 把 `answer` 完整 print 出来看，通常是模型把 JSON 包在代码块标记里或没按 JSON 收尾——重跑一次，或把输出规范的最终格式要求抄全。
