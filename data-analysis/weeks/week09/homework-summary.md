# 个人项目存在的部分问题与改进建议

> 按主题归类整理。每类问题给出「现状描述 → 为什么是问题 → 改进建议」，文末附自查清单。

## 一、研究问题与选题定位（最核心）

**现状**：少量作业停留在"表面应用与交互"，研究问题不清晰，说不清自己要回答什么问题、有什么价值。

**为什么是问题**：本课程的核心是"提出问题并应用技术解决问题"。没有清晰的研究问题，后续的数据、分析、产品都失去了靶心。

**改进建议**：

1. 明确成果的定位，二选一（或兼有）：
   - **理论创新**：探索统计模型或预测类模型，如影响机制检验、因子有效性、预测精度对比；
   - **实践价值**：解决某个真实业务问题，如选股辅助、风险预警、用户画像。
2. 鼓励从"展示数据"升级为"回答问题"：不是"我画了价格走势图"，而是"我从走势图中发现了什么规律、验证了什么假设"。

## 二、研究创新与基准对比

**现状**：少量作业选择的是传统而重要的问题（如股票预测、情感分析、风险评估），但既没有说明自己的做法与现有研究有何不同，也没有与现有方法做性能对比，方法直接套用默认配置。

**为什么是问题**：传统问题的好处是有成熟的方法和公开的基准可以参照，但如果只是"跑一遍现成模型"，就没有创新点可言。创新说明和对比实验正是用来证明"你的工作有价值"的关键环节。

**改进建议**：

1. **写清研究创新说明**：在报告开头明确"本工作相对于现有研究/常规做法的差异点"，可以是新数据、新场景、新方法、新组合，哪怕改进幅度小，也要说清楚改在哪里、为什么这样改。
2. **与传统问题就要做对比实验**：如果问题本身是传统而重要的（如收益预测、文本分类），必须设置基线（baseline）对比：
   - 至少包含 1–2 个经典/现有方法作为对照（如：预测问题对比 ARIMA 与线性回归；分类问题对比词典法与逻辑回归）；
   - 用**统一的评估指标和数据划分**比较性能（如 RMSE、MAE、准确率、F1），并用表格呈现结果；
   - 分析"好在哪里、差在哪里"，而不是只报告自己模型的高指标。
3. **传统问题要在方法层面做改进**：既然是传统问题，纯粹的"复现"不构成成果。尽可能做方法层面的改进，常见路径包括：
   - 特征改进：引入新的特征或数据源（如把舆情得分加入价格预测的特征）；
   - 模型改进：更换或组合模型结构、调整适配问题的建模假设；
   - 流程改进：更严谨的验证方式（如时间序列交叉验证代替随机划分）、更贴合场景的损失函数或评估口径。
4. 改进要落在**结果**上：说明改进前后指标变化了多少，哪怕提升有限，也应诚实呈现并讨论原因。

## 三、数据质量与数据工程

**现状**：

- 数据量偏少，时间范围太短（如仅近 1–3 个月），领域类型单一；
- 偏应用方向的选题，数据时效性不足（用的是陈旧数据）；
- 多源数据采集时没有做好汇总与存储，散落在各个脚本和临时文件里。

**为什么是问题**：数据是分析的原料。样本太少导致结论不可信；时效性差导致应用型分析失去意义；多源数据不统一存储，后续无法复现和迭代。

**改进建议**：

1. **优先使用第三方权威数据集**（如 Tushare、AkShare、Kaggle、国家统计局、CSMAR 等），不要优先自采。第三方数据质量高、字段全、可复现。
2. **拉长时间窗口**：一般分析建议至少 1 年以上；涉及周期性、季节性或建模的问题建议 3 年以上。
3. **注意时效性**：应用型选题（如市场监控、舆情分析）必须使用近期数据，并在报告中注明数据截止日期。
4. **多源数据要有统一存储层**：
   - 建议结构：`data/raw/`（原始采集，不修改）→ `data/clean/`（清洗合并后）；
   - 用统一的主键（如日期 + 股票代码）对齐多源数据；
   - 每个数据文件附一个简单的字段说明（来源、抓取时间、字段含义）。
5. 数据采集代码与数据本身分开放置，保证"跑一遍脚本就能重新拿到数据"。

## 四、分析深度（从可视化走向建模）

**现状**：少量作业止步于描述性统计和图表可视化，缺少进一步的统计分析、预测建模或 AI 交互分析。

**为什么是问题**：可视化回答"数据长什么样"，不回答"数据说明了什么、未来会怎样"。课程要求产出有内核的分析，而非图表堆砌。

**改进建议**（按递进层次，至少做到第二层）：

1. **描述层（基础）**：分布、趋势、相关性可视化——这是起点不是终点。
2. **统计推断层**：假设检验、回归分析、分组对比、显著性检验，回答"差异/关系是否真实存在"。
3. **预测建模层**：时间序列（ARIMA 等）、机器学习（回归/分类）预测，用训练/测试集划分和明确的评估指标（RMSE、准确率等）说明模型效果。
4. **AI 交互分析**：利用大模型对文本/非结构化数据做情感分析、主题提取等，并与量化指标（如收益率）建立联系（可参考本周 NLP 案例）。

## 五、产品形态（内核优先）

**现状**：少量作业把 APP 或 Streamlit 应用当作核心成果，花大量精力在界面上，分析内核单薄。

**为什么是问题**：APP、Streamlit、Flask 都只是"壳"。评价的核心是壳里装的东西——数据、分析、模型。壳做得再好看，内核空洞依然是低分作业。

**改进建议**：

1. **核心成果 = 数据 + 分析 + 模型**，交付物以分析报告、Notebook、模型代码为主。
2. Streamlit / APP **仅用于产品 demo 展示**：把已完成的分析和模型包装成可交互的界面，属于锦上添花，不是主体。
3. 合理的精力分配参考：数据采集与清洗 30%、分析与建模 50%、产品展示 20%。
4. 展示时先讲"研究问题—方法—结论"，再演示产品界面；而不是反过来。

## 自查清单（提交前逐条核对）

- [ ] 研究问题清晰，并说明其理论创新点或实践价值
- [ ] 写明了与现有研究/常规做法的差异点；传统问题设有基线对比并报告指标变化
- [ ] 优先使用了第三方权威数据集，并注明来源
- [ ] 数据时间范围足够（≥1 年），应用型选题数据截至日期较新
- [ ] 多源数据有统一的存储结构（raw / clean）
- [ ] 除可视化外，至少有统计推断或预测建模其中一层，且有效果评估
- [ ] 分析与建模占主要工作量，Streamlit/APP 仅作为 demo 展示层
- [ ] 汇报顺序：问题 → 方法 → 结论 → 产品演示
