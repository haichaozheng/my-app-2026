# 用户洞察方法论

> **引入时机**：W3 | **核心挑战**：我访谈了5个人但提炼不出痛点，如何系统性地从用户对话中发现需求？ | **层级**：Essential

## 为什么要在项目阶段学习这个知识点？

在PBL课程中，你做的不是课堂练习，而是面向真实用户的产品。一个金融数据分析产品如果解决的不是真实痛点，再精美的可视化也只是"自我感动"。很多团队在项目初期都会犯同一个错误：基于自己的想象定义需求——"投资者肯定需要实时行情推送""分析师一定想要复杂的量化模型"——然后花几周时间开发一个没人用的功能。

用户洞察方法论就是帮你避免这种"假想需求"陷阱的工具。通过系统性的用户访谈和需求分析，你可以从真实用户的对话中提炼出被掩盖的痛点，构建出有血有肉的用户画像，最终设计出解决真问题的产品。

很多同学做了用户访谈但觉得"没什么收获"——不是因为用户没有痛点，而是因为你的访谈方法和分析方法有问题。"你需不需要一个XXX功能？"这种直接提问只会得到礼貌性的"可能需要吧"，无法揭示真正的需求。你需要学会像人类学家一样观察和倾听，像侦探一样追问和验证，才能从看似平常的对话中发现真正的洞察。

## 这个知识点的核心内容

### 访谈技巧

**避免"你要不要"式提问**

最糟糕的访谈问题是直接问用户"你需不需要某个功能"——人们不擅长预测自己的需求，往往会给出迎合性回答。

- 差的提问："你需要一个股票筛选工具吗？" → "应该需要吧"
- 好的提问："你上一次选股票的时候是怎么操作的？遇到了什么困难？" → 真实行为和痛点

**The Mom Test原则**

Rob Fitzpatrick在《The Mom Test》中提出了三条访谈铁律：

1. **谈论具体经历而非泛泛观点**：问"你上次做XX是什么时候、怎么做的"而非"你觉得XX怎么样"
2. **关注行为而非意愿**：问"你目前是怎么解决这个问题的"而非"你会不会用某个方案"
3. **不要直接问"你会不会用"**：用户无法预测未来行为，但过去的真实行为是最好的预测指标

**追问技巧**

- **"能具体说说吗？"**：当用户提到一个模糊概念时，追问具体细节
- **"上次遇到这种情况是什么时候？"**：从抽象回到具体经历
- **"你当时是怎么解决的？"**：了解现有解决方案的不足
- **"这个过程中最麻烦的是什么？"**：直接定位痛点
- **"如果有一个工具能帮你做XX，你会怎么用？"**：验证解决方案的方向（但注意这只作为参考，不是确认）

### 从对话中提炼痛点

访谈后，你需要从原始对话中提炼出结构化的痛点。推荐使用以下方法：

**痛点分类框架**

将用户提到的问题按照以下维度分类：

| 维度 | 含义 | 示例 |
|------|------|------|
| 功能痛点 | 缺少需要的功能 | "我找不到一个工具能同时看多只股票的财务数据对比" |
| 效率痛点 | 现有方式太慢太繁琐 | "每周我都要花2小时手动从Wind导数据再整理到Excel" |
| 质量痛点 | 现有方案结果不够好 | "Excel算的指标经常出错，公式一拉就错" |
| 体验痛点 | 使用过程痛苦 | "那个软件界面太复杂了，找不到我要的功能" |
| 认知痛点 | 不知道该怎么做 | "我不确定这个行业该用PE还是PB来估值" |

**痛点评估矩阵**

不是所有痛点都值得解决，用以下矩阵评估：

```
            高频
             |
    优先解决  |  值得解决
             |
低价值 ------+------ 高价值
             |
    可以忽略  |  锦上添花
             |
            低频
```

- 高频+高价值：核心痛点，优先解决
- 高频+低价值：可能只是表面痛点，深入挖掘背后是否有更深层问题
- 低频+高价值：小众但重要的需求，可以作为差异化特色
- 低频+低价值：可以忽略

### 共情地图（Empathy Map）

共情地图是一种将用户访谈信息可视化的工具，帮助团队从用户视角理解需求：

```
┌──────────────┬──────────────┐
│   说了什么？   │   做了什么？   │
│ 用户直接说出的  │ 用户实际的行为  │
│ 问题和需求     │ 和操作         │
├──────────────┼──────────────┤
│   想了什么？   │   感受了什么？  │
│ 用户的想法和    │ 用户的情绪和    │
│ 考虑          │ 担忧           │
└──────────────┴──────────────┘
```

**示例**：访谈一位个人投资者

- **说了什么**："我主要看基本面选股，偶尔参考技术面"
- **做了什么**：打开东方财富看PE、PB，切到同花顺看K线，再用Excel手动记录
- **想了什么**："这么多数据，我不知道哪个指标最重要""不同网站数据还不一样"
- **感受了什么**：焦虑（怕选错）、疲惫（多工具切换）、不确定（数据来源矛盾）

从共情地图可以发现，这位用户的痛点不只是"缺一个功能"，而是"信息分散导致决策焦虑"——这提示产品方向应该是"整合多源数据的决策辅助工具"而非简单的"数据查询工具"。

### 用户画像构建

基于多个用户访谈，构建典型用户画像（User Persona），用于指导产品设计：

```markdown
## 用户画像：张同学

**基本信息**：财经院校大三学生，金融学专业，有基础Python能力

**目标**：
- 找到适合长期持有的优质股票
- 学以致用，将课堂知识应用到实战分析

**行为特征**：
- 每天花30分钟看财经新闻和个股公告
- 用东方财富APP看行情，Excel做简单分析
- 偶尔用Python跑一些数据，但代码经常报错
- 会在雪球、股吧看其他人的分析

**痛点**：
- 不确定自己的分析方法对不对（认知痛点）
- 多个工具切换很麻烦，数据对不上（效率痛点）
- 找不到适合自己水平的分析工具（功能痛点）

**引用**：
"我知道ROE很重要，但不知道多少算高、怎么跟同行比"
"我想用Python分析，但每次都花大量时间处理数据格式问题"
```

## 关键细节与易错点

### 把自己的需求当作用户需求

这是最常见的错误。作为课程参与者，你对数据分析工具有自己的理解和需求，但这不代表你的目标用户也有同样的需求。比如你觉得"需要高级统计建模功能"，但你的用户可能只是想"快速看几只股票的估值对比"。始终从用户访谈中验证需求，而非从自己的假设出发。

### 样本量太小导致偏误

5个访谈对象足以帮你发现痛点，但不足以确认痛点的普遍性。如果5个用户中有3个提到同一个问题，这值得重视；但如果只有1个提到，可能是个人偏好。在资源有限的情况下，优先解决被多个用户独立提到的痛点。

### 只听"说"不看"做"

用户说的和做的经常不一致。有人说"我很重视基本面分析"，但实际操作中只看K线图。访谈时不仅要听用户怎么描述自己的行为，还要追问具体操作步骤，甚至观察用户的实际操作过程。

### 访谈中引导性提问

"你不觉得现在的股票分析软件太复杂了吗？"——这种问题已经暗示了答案。应该问"你现在用的分析软件有什么让你不满意的地方？"让用户自己描述问题，不要把你的观点注入问题中。

### 痛点与解决方案混淆

"我需要一个实时推送股票涨跌的APP"——这是解决方案，不是痛点。真正的痛点可能是"我总是错过买卖时机"或"我不想一直盯盘"。痛点是问题，解决方案是回答——你需要从用户提出的解决方案中反推出真正的痛点。

## 金融数据分析示例

**场景**：你的团队想做"金融数据可视化仪表板"产品，需要访谈金融从业者了解他们的数据分析痛点。

**访谈对象**：5位金融从业者（2位券商研究员、1位基金经理助理、2位个人投资者）

**访谈记录片段**：

研究员A："我每天早上要花一个小时从Wind导数据，整理到Excel里做行业对比表。最烦的是Wind的导出格式跟Excel的格式经常不兼容，每次都要手动调整。"

研究员B："我们组主要做行业研究，但申万行业分类和Wind行业分类不一样，每次对齐分类都要花半天。而且很多小公司的研究报告根本找不到。"

基金经助："我帮基金经理每天更新持仓的风险指标，VaR、波动率这些。现在是用Excel算的，但每次新增一只股票就要改好多公式，特别容易出错。"

个人投资者C："我就是想看看我那几只股票最近怎么样，但每个APP都给我推一堆我不关心的信息。我就想知道持仓赚了亏了多少，跟大盘比怎么样。"

个人投资者D："我学会计出身，比较看基本面，但不知道怎么系统地分析一家公司。PE、PB、ROE这些我都知道，但不知道怎么综合判断。"

**痛点提炼**：

| 痛点 | 类型 | 频次 | 价值 |
|------|------|------|------|
| 多工具切换，数据格式不兼容 | 效率 | 3/5 | 高 |
| 行业分类标准不统一 | 效率 | 2/5 | 高 |
| Excel公式易出错 | 质量 | 2/5 | 高 |
| 信息过载，需要个性化筛选 | 体验 | 2/5 | 中 |
| 不确定分析方法是否正确 | 认知 | 2/5 | 中 |

**用户画像**（综合5位访谈对象）：

目标用户是"需要日常数据分析但缺乏高效工具的金融从业者/学习者"，核心痛点是"数据获取和处理占用了太多本应用于分析的时间"，产品方向应该是"整合多源数据、提供标准化分析流程的工具"。
