## 一、总体判断

课程骨架优秀，属于国内同类课程中少见的高完成度设计：

- **PBL 六要素齐备**：真实问题（金融社区痛点）、持续探究（17 周迭代）、学生自主权（三档选题+三选一实验）、反思（双层日志+DSR 自检）、同伴 critique（W9 互评）、公开产品（公网部署+路演）。
- **知识锚定式里程碑**：交付物同时评价"做得好不好"和"体现了哪个知识概念"，直接支撑知识迁移与重构——这是最有辨识度的设计亮点。
- **Just-in-time 知识引入**：Challenge→Gap→Knowledge→Apply 节奏在 knowledge-map 中有系统落地，且反思日志的 feed-forward（5.1 追踪缺口是否真补上）形成了闭环。
- **版本号式产品演进**：v0.1→v0.2→v0.3→v0.4→v1.0→v1.1 给学生清晰的进度感和成就阶梯。
- **DSR 方法论锚定**：为"产品兼产论文"打通学术合法性，且以"轻量适配原则"控制了对本科生的侵入度。

主要问题集中在三类：

1. **跨文档一致性问题**（以周 plan 为基准）：核查发现 8 处措辞与同步项（见第三章），主要两类：a) plan 缺工作流所需的显式步骤——W2 opencode 只写"读取 AGENTS.md"，缺"创建仓库+AGENTS.md"步骤（创建安排在 W2 随 opencode 课堂是合理的 just-in-time 设计，但目前只有一半）；b) plan 与 milestones 措辞不齐——W2"候选方向"的颗粒度（"不急于选题"vs milestones"初选 2-3 个方向"）与交付物命名。注：W2"不急于选题+锁定社区"是社区先行的设计意图（先入社区倾听，借社区真实问题反哺选题），**不是矛盾**，但表述未点明意图，易被误读。总方案层面的多数偏差不必处理——按 plan 再生成时自然携带或消解。
2. **周粒度教学设计不完整**：所有 plan 均缺学习目标、时间预算、评分锚点、求助路径、兜底方案五要素——plan 是"任务清单"而非"学习设计"，学生看到的是"要交什么"而非"要学会什么、卡住了怎么办"。
3. **负荷分布失衡**：W4、W11、W15 三周为"双线程极高负荷周"，违反"一周一个新重概念"的节奏控制；W3 存在环环相扣的"单点崩溃风险"。

另有**结构性缺位**（全部 `lecture.md`/`lab.md` 为 0 字节；knowledge-map 引用的 `weeks/weekXX/resources.md` 不存在；rubric 计分的"技能小练 8-10 次"无实体），属全局文档工程问题，列入附录 P5。

### 2.2 跨周体验问题（7 项）

1. **首胜延迟**：第一个"能用的产品"要到 W7，前 6 周交付物全部是报告/清单/文档。对"想做出东西"的本科生，动机前 6 周靠信任支撑。缺一个早期"产品触感"时刻（哪怕 30 分钟跑通一个往届示例）。
2. **文档负担重**：W1-W15 连续 15 周交付 + 每周 7 节反思日志 + repo 内 journal + 40 个知识节点勾选表。元认知设计初衷极好，但对本科生体量偏重，后期大概率退化为仪式性应付——恰恰损失了反思的教育价值。
3. **求助路径从未出现**：17 份 plan 没有任何一处说明"卡住了找谁、多久有响应"（办公时间？课程群？互助组的职责边界？教师承诺的答疑节奏？）。唯一支持结构是互助小组，但小组只能解决"愿意回答的问题"，部署失败、账号被封这类问题无人接住。
4. **无时间预算**：每周从未标注预期课外工时。长项目课程最常见的失败模式就是学生在 W4/W11 才发现"这周要 15 小时"，进而挤占其他课程或抄近道。
5. **有"交"无"馈"**：没有任何一周承诺交付物由谁、何时、以何种形式反馈。形成性评估只完成了"形成"，没有"反馈"。
6. **工具栈漂移**：W1 Trae 主力 → W2 opencode 必装必会 → W3 OpenCode Skill 讲座，三周三个新入口，每个都要求"熟练使用"级别投入。工具是手段，但入门成本真实存在。
7. **社区线断裂 8 周**：W1-W3 深度沉浸社区（发现、加入、倾听、访谈），W4-W11 完全消失，W12 才以"获客"名义重启。产品建设期恰恰是最需要"用户共情保温"的阶段——学生闭门写代码 8 周后，W13 要他们突然回到真实用户面前收集反馈。

## 四、教育学专家视角

### 4.1 亮点（应保留并在修订中强化）

1. **知识锚定里程碑**：把"评价任务表现"与"锚定概念理解"合一，是 constructive alignment（Biggs）的教科书式应用。
2. **feed-forward 反思闭环**：反思日志 5.1"上周缺口是否真补上"把Reflection从记录升级为调节（metacognitive regulation），多数 PBL 课程做不到。
3. **布卢姆弧线清晰**：理解/应用（W1-5 报告类）→ 应用/分析（W6-10 构建类）→ 分析/评价（W11-15 建模评估）→ 创造/评价（W16-17 路演与重构）。评价类任务占比在后半程显著上升，符合高阶能力培养目标。
4. **W3 提案准入清单 8 项过审 + W9 结构化互评**：两个高质量的评估性学习事件（evaluative events），有明确标准、有真实后果、有迭代回路。
5. **选做/必做分层意识**：RAG 选做、Skill 可选产品形式、三选一实验、进阶自学——在统一脊柱上保留了弹性。

### 4.2 问题（按教育学金字塔分层）

1. **学习目标缺失（影响最大）**：17 份 plan 全部只有"教学内容/项目活动/交付物"三件套，无一陈述可测量学习目标。缺少目标导致：a) 学生无法自我监控"这周我达标了吗"；b) 教师无法判断内容是否超载（没有目标就没有取舍依据）；c) 评分锚点悬空（rubric 评产品，平时成绩评提交，唯独"学到什么"无显式检验点）。
2. **反馈系统未设计**：除 W3 过审与 W9 互评外，W4-W8 的形成性交付物无任何反馈承诺。PBL 的核心机制是"迭代"，迭代的前提是"反馈"——没有反馈的每周交付会退化为"为交而交"，错误（如数据落盘不规范、分析逻辑错误）一路复利进入 MVP 与最终产品。
3. **形成性评分透明度不足**：平时成绩 30%"综合评分、不细分比例"给了教师灵活度，但对每周都在提交的学生是黑箱。rubric 第五节做了"标准-维度-证据"映射（好），却未映射到每周交付物的分数预期。
4. **"组内项目平均 10%"的公平性风险**：以他人项目表现给个人计分，违背"成绩反映个体成就"的基本评估伦理；rubric 自己的"防套利说明"已承认该机制在均匀通胀下失效。作为激励设计的意图（赋能同伴）值得保留，但实现方式会造成：a) 被组内弱者拖分的焦虑与排斥；b) 强者无需互助也能拿满——激励方向并不如预期稳定。
5. **认知负荷控制失当**：W4/W11/W15 各引入 2 个以上全新重型概念域（split-attention + 高内在负荷叠加），恰与学生"独立项目首次遇到真实工程问题"的时段重叠。SWEL（工作示例效应）与专家逆转效应提示：这一阶段学生最需要的是 worked example 与分步脚手架，而非多线并进。
6. **无兜底/回退路径（equity 问题）**：计划隐含假设：每人有稳定网络与可用电脑、腾讯云额度顺利获批、LLM API 有费用承受力、身边能找到 5 个目标用户、W3 提案一次通过。任一假设不成立的学生会立刻掉队，而课程没有为"掉队"设计任何台阶。财经本科生编程背景参差（先修只要求"一定 Python 基础"），这一人群尤其需要 fallback。
7. **学术术语支架不足**：criterion validity claim、参考实体、Gregor & Hevner 知识贡献象限、DSR 七指导原则自检——这些对博士生也偏抽象。总方案有"轻量适配原则"，但 plan 层（学生每周真正读的那页纸）零白话转化、零示例。W15 教学条目 3 直接出现"Larsen 2025：每产品≥1 条 criterion validity claim"——这是术语，不是教学设计。
8. **同伴互依是自愿性的，非结构性的**：互助小组的"互助"没有任务结构支撑（谁在何时为谁做什么、产出什么）。组内项目平均 10% 用分数倒逼互依，但缺了"互依的机会与脚本"。Topping 的同侪辅导文献一致表明：无角色、无共同产出、无训练的同侪互助，实际发生率低且质量不稳。
9. **期中形成性校准缺失**：协作行为（互评、贡献记录）只在 W17 期末一次性 360° 评估——学生第一次被要求"正式评价同伴"就用于计分，且没有期中数据可供纠偏。

### P1 plan.md 统一结构模板 — 每周新增 5 要素

现状结构：`主题 / 教学内容 / 项目活动 / 交付物 / 课后作业 / 学习资料`。
建议升级为：`主题 / 本周学习目标 / 预计投入 / 教学内容 / 项目活动（三层任务） / 交付物（含评分锚点） / 卡住了找谁 / 课后作业 / 学习资料`。

五个新增要素的写法规范：

**① 本周学习目标**（2-4 条，可测量，行为动词+条件+标准）

> 示例（W5 重写）：
> - 能针对本项目数据集说出清洗策略的理由：对每类缺失/异常说明"删还是补、为什么"
> - 能从分布/趋势/关联等至少 3 个视角完成 EDA，并说明每个视角的选择理由
> - 能用 Prompt 让 AI 辅助发现至少 3 条自己未预想到的洞察，并对其中 1 条做可信度判断

**② 预计投入**（课外工时预算 + 与学业其他部分的冲突提示）

> 示例：`本周预计课外 8-10h（数据分析课程通常占大头的一周）；W4/W11/W15 约 12-15h，建议提前与其他课程作业错峰`

**③ 评分锚点**（交付物链接到 milestones 小节与 rubric 维度，附提交前自检清单）

> 示例（W5 交付物行）：
> `个人 EDA 报告 —— 规格与知识锚定见 milestones §2.2；计入平时成绩（形成性）；提交前自检：清洗策略是否给了理由？≥3 视角？附 1 个 Prompt 洞察对话记录？`

**④ 三层任务**（必做/进阶/兜底，替代现在散落在正文里的"可选"混排）

> 示例（W8）：
> - 必做：LangChain Chain + Prompt Template 构建 LLM 解读功能，接入 MVP（v0.2）
> - 进阶：把解读升级为 RAG 问答（提前做 W9 选做）
> - 兜底：API Key 申请失败/额度用尽 → 使用课程提供的演示 Key 完成本地功能验证，部署周（W10-W11）再换自己的 Key

**⑤ 卡住了找谁**（求助升级链，每周 plan 底部一行固定呈现）

> 示例：`卡住 → ①先问 AI（附截图问法）→ ②互助组（当日）→ ③课程群（教师承诺 24h 内响应）→ ④周三办公时间（1v1）。部署/账号类问题直接走 ③。`

### P2 负荷再平衡 — 5 项调整（前后对比）

**2.1 W4 降坡（手动流程周）**

| 项 | 调整前 | 调整后 |
|---|---|---|
| 项目活动 | 获取+落盘+（采集+合规）+手动分析+手动转代码 | 获取+落盘+手动完整分析+边界/假设记录 |
| 交付物 | 数据集+手动分析报告+手动→自动转化代码 | 数据集+手动分析报告 |
| 去向 | — | "手动转代码验证结果一致"并入 W5 项目活动（W5 本就要写清洗代码，正好承接；且转化后的代码直接服务于 W5 EDA） |

理由：W4 的真实瓶颈是数据获取的工程时间（限流、复权、反爬），把自动化转化推后一周既不损失"先手动再自动"的教学理念（W5 开头 15 分钟回顾即可），又能消除全课程最陡的一周。

**2.2 W10-W11 拆线（部署与建模分离）**

| 项 | 调整前 | 调整后 |
|---|---|---|
| W10 作业 | 打磨+云申请+部署方案+阶段反思 | 增加"方案获批后即刻试部署（允许失败，记录报错即可）" |
| W11 课堂 | 部署执行 + ML 范式 + 划分 + 建第一个模型 | 部署只做验收（10min 排障工作坊，发 FAQ）；课堂重心给 ML 入门 |
| 配套 | 无 | 制作《部署排障 FAQ》（环境、端口、依赖、防火墙、API Key 5 类高频问题），随 W10 plan 发布 |

理由：部署踩坑时间方差极大（有人 1 小时有人 1 天），与"第一个模型"双线程必伤其一。把部署的不确定性留在 W10 作业时段消化，W11 课堂才能聚焦建模新概念的引入。

**2.3 W15 瘦身**

| 项 | 调整前 | 调整后 |
|---|---|---|
| 教学内容 | 8 项（评估/交叉验证/偏差方差/有效性 claim/模型嵌入/evals/进阶/UX/路演叙事） | 5 项：评估深入、有效性 claim（白话版+2 个示例）、模型嵌入产品、evals 回归测试、UX |
| 路演叙事+PPT/Demo 制作 | W15 课堂+交付物 | 移入 W16 课堂前段（W16 现为"教学内容一行字"的轻周，正好容纳）+W15 周末仅完成 PPT 大纲 |
| 交付物 | 产品 v1.1 + 路演材料 | 产品 v1.1（含模型+评估+文档）；路演材料仅要求"PPT 大纲+Demo 脚本"，完整材料 W16 课上完成 |

理由：评估与产品化是 DSR 严谨性的落点（Larsen 有效性、criterion claim），需要消化时间；路演叙事是另一个能力域，塞在同一周两头都做浅。W16 原本教学密度过低，恰好承接。

**2.4 获客窗口拉长（W11→W13 滚动）**

| 项 | 调整前 | 调整后 |
|---|---|---|
| 用户触达起点 | W12"设计推广渠道，开始触达" | W11 部署成功当天即发产品链接（班级群/朋友圈/已加入的社区），触达不占 W12 教学时段 |
| 反馈回收 | W13 单周收 5-10 条 | W11-W13 滚动收集，W13 集中做"分类分析与迭代决策"（教学重心后移到分析而非催收） |
| 兜底 | 无 | a) 教师建立"课程互助测试池"（全班互为用户的登记墙）；b) 社区运营者/校友用户由教师转介；c) 实在不足 5 人时允许"3 人深度访谈"替代"5-10 条记录"（rubric 的用户反馈维度按深度而非数量给分） |

理由：用户回复天然有延迟，单周催收会把学生推向"找 5 个同学填个表"的走过场，违背 Relevance Cycle 的真实用户意图；拉长窗口+兜底才能保住真实性。

**2.5 W6 指定为缓冲周（弹性机制）**

| 项 | 调整前 | 调整后 |
|---|---|---|
| W6 交付物 | 可视化原型（必须 Notebook 完整实现） | "核心可视化方案 + 图表设计说明"为必做；交互式实现允许带入 W7 与产品迁移合并完成 |

理由：15 周连轴的项目课程必须预留官方泄洪口，否则欠账以"抄近道/降低质量/心理放弃"的形式隐性出现。W6 负荷天然最低，是指定的缓冲带。
