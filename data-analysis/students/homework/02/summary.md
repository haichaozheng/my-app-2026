# 踩坑与爬坑记录

1. 一开始只测试了 5 页，直接跑全量的时候中途断网了一次，前面抓的列表全没了。解决办法：让 opencode 改成边抓边存、支持断点续传，再断了直接重跑就行。断点续传那个是我自己想到要存中间结果，让它帮我改的，列表每页存一次 json，正文每抓一条追加一行 jsonl。

2. 中文乱码。网页原始编码为 GB 系编码，requests 自动识别不准；且 Windows 控制台默认 GBK，打印采集日志时中文全部乱码，难以定位问题。解决办法：requests 请求后设置 r.encoding = r.apparent_encoding 正确解码中文；程序日志用 sys.stdout.reconfigure(encoding="utf-8") 避免控制台乱码；写入 docx 的内容不受控制台编码影响。

3. 详情页标题解析错误：采集完成后发现大量新闻标题显示为「西财要闻」而非真实标题。原因是详情页 HTML 第一个 <h3> 是页面左侧导航栏的文字「西财要闻」，脚本解析时取到了第一个 <h3> 作为标题，覆盖了从列表页得到的正确标题。解决办法：通过 opencode 检查详情页 HTML，对全部 <h3> 标签输出调试信息，发现索引 0 的 <h3> 是「西财要闻」（导航），索引 2 才是正文标题。据此修改脚本：标题以列表页 <h3> 为准，不再用详情页标题覆盖；再编写修复脚本重抓全部列表页标题，将 2407 条错误标题全部更正，校验 0 条残留。

4. 分页 URL 编号倒序：一开始按常规思路猜测分页为 xcyw/2.htm、xcyw/3.htm……，但打开全是 404 或重复内容。观察列表页底部分页发现编号是倒序排列（240、239、…、1），需要重新推导 URL 规律。解决办法：直接查看浏览器开发者工具中「下页」「数字页码」的链接，发现第 2 页指向 xcyw/240.htm、第 3 页指向 xcyw/239.htm、尾页指向 xcyw/1.htm。于是构造规律：第 1 页 = xcyw.htm，第 n 页 = xcyw/(242-n).htm（n≥2），并在脚本中按此生成全部 241 个页面 URL。

5. 高频请求被服务器中断：初次全量抓取详情页时，请求过于密集导致 curl 进程被服务器断开（Terminated），连接超时，后续 URL 大量失败。解决办法：通过 opencode 询问解决办法后，采用以下策略：降低并发（4 线程）、每次请求后设置随机小延迟（约 0.2 秒）、添加浏览器 User-Agent 与 Referer 头信息、并为每个请求设置超时与 3 次重试；同时加入断点续传，失败请求留到下一轮补齐。重跑后详情页全部抓取成功（2407/2407）。

6. 参考 Opencode 文档优化提示词，明确规定输出字段、csv 格式，要求代码增加清洗逻辑；先小批量测试，确认格式无误再全量采集。不再笼统写"抓取西财新闻"，提示词直接列明标题、发布时间、链接、正文等输出字段，指定 csv 表头；先仅抓取 1 页新闻样本，打开 csv 核对字段对齐、排版正常，再执行完整批量采集任务。

7. 选择模型方面，我最开始选择了 Muse Spark 1.3 Free 模型，但是在执行对话任务仅一次后，它便反复显示 "This model is unavailable in your country."，询问豆包得知这是正常现象后，我选择了 Big Pickle 继续我的任务。

8. 保存文件出现模糊字符：将文件保存为 UTF-8 BOM 格式（添加了 EF BB BF 字节序标记）；规范化了中文引号、破折号、全角标点等特殊字符；重新打开 swufe_news_full.json 文件，模糊字符警告消失。

9. opencode 自主调试终端乱码：我只是在对话里告诉 opencode："请直接运行这个脚本。如果有报错（比如网页结构不对、编码错误、找不到分页），请自己分析报错原因并修改代码，直到成功采集并生成 csv 文件。"它开始运行后，终端出现了  乱码（图4）。opencode 敏锐地发现这其实是 PowerShell 对 f-string 支持的问题。它没有要求我修改终端，而是主动新建了一个 test_scraper.py 测试脚本（图5、图6），在脚本里加入了 io.TextIOWrapper(sys.stdout.buffer, encoding="utf-8") 强制修正编码，并且重新解析了列表页。测试结果确认列表解析正常（10 条），且存下来的数据没有乱码，只是终端显示问题。
