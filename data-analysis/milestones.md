# 数据分析与可视化 — 阶段里程碑与交付物定义

本文件定义每个交付物的基本规格和**知识锚定要求**——交付物不仅评价"做得好不好"，还要求显式体现特定知识概念的应用。知识锚定确保学生把项目经历重构为可迁移的知识框架。

> **交付物归属说明**：本课程为"一人公司(OPC) + 互助小组"模式，互助小组（鼓励5人一组）**不要求共享同一条赛道或领域**，但**每人独立完成并交付自己的产品**。各里程碑均为**个人交付物**（除注明外）。交付物按评分归属分为两类，避免同一交付物重复计分：
> - **归属「平时成绩·其他条目」（形成性，满分40分）**：技能小练(lab) + 以下标注的形成性里程碑
> - **归属「个人项目」（终结性，满分50分）**：最终产品与项目报告相关里程碑
> - 协作互评（满分10分，计入平时，期末 W17 评定）见 `templates/peer-review.md`，不按里程碑重复计分

## Phase 1: Idea Stage（W1-3）

### 1.1 互助小组协议 + 社区调研记录（W1）

**基本规格**：
- 鼓励5人一组组成互助小组，打印签署 `templates/group-agreement.md`（成员表注明专业背景和技能优势）
- 基于工具/方法互助组建小组，选题可不同领域；每人独立交付产品
- 每人提交社区调研记录（`templates/community.md` 全文）：进入一个社区场合（线下到场 / 线上可旁听 / 需要才注册），原话 ≥3 条，再从中抽出数据分析产品可能服务的用户群
- 公约问卷（`pic/class-norms.png`）课后填写，供 W2 课堂分析

**知识锚定要求**：
- 体现对"一人公司 + 互助小组"模式的理解：协议写明独立交付、不代跑
- 体现AI辅助编程工具的初步使用：附个人环境配置截图或记录
- 体现社区先行：先有场合和原话，再抽出用户；能说明「人和数据分析产品对得上」，并用原话而非概括作为证据

> 注：个人项目仓库与 AGENTS.md 的创建安排在 W2 随 opencode 课堂完成（先创建、再被 opencode 读取），见 §1.2。W1 已交的 `community.md` 在 W3 拷入 `docs/community.md` 后继续追加。

---

### 1.2 个人赛道意向 + 项目仓库（W2）

**基本规格**：
- 候选方向：从三档选题来源（财经新闻/真实需求/个人爱好）列出 2-3 个候选方向但**不锁定**——W3 将用社区真实问题收敛调整（参考菜单见 `project-selection-guide.md`）
- 对每个候选方向做数据可得性初验（实拉一次数据，确认能跑通），初步调研其数据源和用户群体
- 将 W1 社区调研迁入仓库并继续倾听——用户须从该社区原话中抽出；原话追加到 `docs/community.md` 第 4 节（W1 已须 ≥3 条，未齐者本周补齐）。入社区本身即选题探索的一部分（社区先行）
- 初始化个人项目仓库：git 建 repo；用 opencode 在根目录新建 `AGENTS.md`；在 `docs/` 新建 `requirements.md`、`design.md`、`scope.md` 骨架（对照 `templates/`）；放入 `docs/journal.md` 与 `docs/community.md`

**知识锚定要求**：
- 体现金融数据生态知识：至少列出2个可用的金融数据源/API，并说明其覆盖范围和获取方式
- 体现Prompt驱动的数据探索：展示至少1个用Prompt探索赛道数据的对话记录和发现
- 体现选题方向探索方法：说明你从哪档来源得到候选方向，以及数据可得性初验的过程
- 体现 AI-Native 项目工作流起步：仓库链接可访问；根目录有 `AGENTS.md`；`docs/` 有 `requirements.md`、`design.md`、`scope.md`（骨架级即可）

### 1.3 问题陈述初稿（W3）

**基本规格**：
- 清晰描述金融领域的具体痛点
- 说明目标用户是谁、他们目前如何应对该痛点
- 初步判断问题的重要性和解决价值
- 说明痛点来自真实用户验证（而非假设），并描述目标用户当前如何应对该痛点
- 附社区调研记录：仓库内 `docs/community.md`（社区/场合名称、进入方式、观察期、≥3 条用户原话或当面原话、从中识别的痛点）

**知识锚定要求**：
- 体现社区先行方法的应用（必做）：说明加入的社区、倾听阶段记录的痛点证据、痛点如何从社区真实对话/观察中提炼而非假设
- 区分"假设的问题"和"验证的问题"：标注哪些痛点来自用户对话/社区观察（验证的），哪些来自团队假设（待验证的）
- 体现痛点验证逻辑：痛点不是凭空想象的，而是从用户访谈/社区观察中识别并验证的——说明你的痛点发现路径

---

### 1.4 项目提案（W3，与问题陈述初稿同周提交）

**基本规格**：
- 问题定义：要解决的金融痛点和目标用户
- 项目目标：产品要实现什么功能、解决什么问题
- 数据来源：将使用哪些金融数据源
- 初步方案：技术路线和产品形态
- 互助小组内互助设想（你将如何借助小组在工具/方法/AI应用上互助加速个人项目）
- 通过 `project-selection-guide.md` 选题准入清单（8项）过审，不达标须调整或重选
- 本提案以 `docs/requirements.md` 形式提交（模板见 `templates/requirements.md`，须含"问题与用户"第一节）

**知识锚定要求**：
- 体现选题来源：明确说明选题命中哪档来源（财经新闻驱动/真实需求驱动/个人爱好），并解释为何这是真实需求而非假想
- 体现项目筛选逻辑：用Andrew Ng框架或其他标准说明"为什么这个项目值得做"（可行性、价值、独特性至少考虑其中2项）
- 问题-方案匹配论证：说明为什么你的方案能解决你定义的问题（而非"我觉得可以"）

## Phase 2: MVP Stage（W4-10）

### 2.1 手动分析报告（W4）

**基本规格**：
- 编写数据获取脚本（AKShare/Tushare/requests/crawl4ai等），处理限流/复权/对齐，落盘为项目数据集（CSV/DuckDB/Markdown，含字段说明）；若含网页采集须附合规自检清单
- 在项目数据集上手动完成一次从数据到洞察的完整分析流程
- 分析报告包含：数据来源、分析步骤、中间发现、最终洞察
- 说明哪些步骤未来可自动化为产品功能
- 产出 `design.md`（技术方案，模板见 `templates/design.md`）与 `scope.md`（范围与任务，模板见 `templates/scope.md`）作为后续构建依据（项目工作流见 `teaching-plan.md`）

**知识锚定要求**：
- 体现数据分析思维链：不是罗列图表，而是展示从数据到洞察的逻辑推导过程（每一步"为什么这样做"、"发现了什么"、"下一步做什么"）
- 体现手动流程先行理念：说明手动分析验证了什么价值，以及哪些环节适合自动化
- 体现批判性思维与判断：对至少1个关键洞察做偏误自检（是否可能存在确认偏误、幸存者偏差等），或对AI辅助生成的分析结果做可信度判断
- 体现金融数据获取与落盘能力：说明数据源选择理由、获取脚本设计、限流/复权/对齐处理方式、落盘格式选择的理由（而非"调通即可"）

---

### 2.2 EDA报告 + 手动→自动转化代码（W5）

**基本规格**：
- 数据清洗过程和结果
- 探索性数据分析的可视化和发现
- 数据质量评估
- 手动→自动转化代码（将 W4 手动流程转化为代码，附与手动结果的验证对比；原属 W4 规格，随转化一并移至本周）

**知识锚定要求**：
- 体现数据清洗方法论：不是"我把缺失值删了"，而是说明清洗策略选择理由（如：为什么删除而非填充？为什么用均值而非中位数？）
- 体现EDA多视角分析：至少包含3种分析视角（如分布视角、趋势视角、关联视角），并说明每种视角的选择理由和发现
- 体现Prompt驱动EDA洞察：至少展示1个用Prompt辅助发现洞察的对话记录
- 体现手动→自动的验证闭环：转化代码与手动结果一致（或说明差异原因），转化后的代码可直接服务于 W6/W7 产品构建

---

### 2.3 可视化方案与原型（W6）

**基本规格**：
- 基于W5 EDA发现的洞察，完成核心可视化方案：图表清单 + 每个图表的设计说明 + 叙事逻辑
- 交互式原型在Jupyter Notebook中实现；**允许延至W7与产品迁移合并完成**（W6为弹性缓冲周，欠账可吸收）

**知识锚定要求**：
- 体现可视化设计原则：每个图表类型的选择都有理由（如"热力图而非折线图，因为要展示相关性矩阵而非趋势"）
- 体现可视化叙事逻辑：图表之间存在逻辑递进关系，而非随机罗列
- 至少有1个交互式可视化设计（说明交互的目的：让用户探索什么？）

---

### 2.4 MVP v0.1（W7）

**基本规格**：
- 可运行的产品原型，核心功能可用
- 至少包含数据加载、分析、可视化展示的基本流程
- 部署在本地可运行
- 框架选择：Streamlit（必做），Gradio（可选），或自选框架（React/Vue+FastAPI等，适合有Web开发基础的同学）

**知识锚定要求**：
- 体现快速原型方法论：说明产品核心功能如何对应手动分析报告中已验证的价值环节
- 体现技术选择理由：为什么选择该框架（而非"别人都在用"）

---

### 2.5 MVP v0.2（W8）

**基本规格**：
- 在v0.1基础上用LangChain（Chain+Prompt Template）构建LLM智能解读功能
- AI功能须真实解决用户痛点（非锦上添花）

**知识锚定要求**：
- 体现LangChain Chain与Prompt Template的设计选择：Chain如何组织调用链路、Prompt Template如何约束输出格式与可信度
- 体现AI功能与产品核心价值的关联：AI功能不是"锦上添花"，而是解决用户痛点的关键能力——说明这种关联
- 体现对AI输出的判断：说明你对该AI功能生成的回答做了哪些可信度评估（如测试了哪些边界问题、发现了哪些幻觉或不准确输出）

---

### 2.6 RAG升级（选做）+ 组内个人MVP互评反馈 + MVP v0.3（W9）

**基本规格**：
- 有需要的同学可给产品添加RAG功能（选做升级，知识库素材优先复用W4网页采集的markdown文件和W5的EDA分析结果）
- 对组内其他成员的个人MVP给出结构化反馈（同时作为期末协作互评的形成性依据）
- 根据反馈开始迭代改进自己的MVP，产出 v0.3

**知识锚定要求**：
- （选做RAG）体现RAG知识库设计：知识库包含什么内容、文档切分策略、检索策略如何设计
- 体现产品评审标准的运用：互评反馈应基于明确标准（功能完整度、可用性、分析深度、AI功能价值），而非主观印象
- 体现Critique & Revision方法论：说明收到什么反馈、为什么采纳/不采纳、迭代改进的逻辑

---

### 2.7 打磨迭代 + 上线准备（W10）

**基本规格**：
- 完成根据互评反馈的定向打磨，产出 v0.4（打磨版，可演示）
- 申请腾讯云账号并领取校园/免费额度，确定上线方式（轻量应用服务器 或 CloudBase）
- 若产品使用数据库，完成选型说明：首选 **SQLite**（零安装、文件型、Python 内置 `sqlite3`，适合单用户 MVP）；若需多用户并发写或服务端独立库，选 **PostgreSQL**（开源免费、本地可安装，腾讯云有云数据库免费额度）
- 产出个人上线部署方案（部署目标、进程启动方式、数据库选型与理由、AI功能部署考量：LLM API Key管理、RAG向量库存储位置）

**知识锚定要求**：
- 体现迭代打磨方法论：说明根据反馈优先级排序了哪些改进项、为什么先做这些
- 体现技术债意识：识别并清理了哪些妨碍后续建模增强（W12-W15）集成的代码结构问题
- 体现云部署认知：说明公网可访问与本地运行的关键区别（进程常驻、端口暴露、依赖环境）
- 体现数据库选型逻辑：说明为何选 SQLite 或 PostgreSQL，依据是其产品的并发/部署形态需求，而非"听说好用"
- 体现AI功能部署考量：LLM API Key如何安全管理、RAG向量库在服务端的存储方案
- 体现上线规划：部署方案需考虑 W11 实际部署与 W12-W15 建模增强的后续集成

## Phase 3: Launch Stage（W11-15）

### 3.1 产品公网可访问 + 基础模型（W11）

**基本规格**：
- 产品部署在公网可访问的地址（执行W10部署方案，MVP v0.4含W8 LangChain LLM智能解读）
- 基本运维保障（至少能稳定运行到路演）
- 从个人金融数据建立第一个基础模型：回归或分类，至少其一（**必做基础**）
- 说明训练/测试划分、模型选择理由、初步过拟合自检

**知识锚定要求**：
- 体现云部署知识：说明部署平台选择理由、遇到的部署问题及解决方式
- 体现从本地到公网的产品化思维：部署过程让你发现了哪些本地开发时忽略的问题？
- 体现机器学习建模基础：不是"调库跑通"，而是说明为什么选回归/分类、特征从哪来、训练/测试如何划分、如何判断是否过拟合

---

### 3.2 模型迭代版 + 获客进展记录（W12）

**基本规格**：
- 完善特征工程与模型选择（**进阶可选**：时间序列/因子模型/无监督）
- 简单评估与过拟合自检
- 获客进展记录：复盘 W11 部署当天已开始的触达，调整并扩大渠道（反馈 W11-W14 滚动收集）

**知识锚定要求**：
- 体现特征工程与模型选择逻辑：特征如何构造、为什么选该模型、如何避免数据泄漏
- 体现对决策树/随机森林的理解：为何用树模型升级或对比线性基础模型、特征重要性如何反哺特征工程
- 体现朴素贝叶斯自学成果：一句话说明其直觉与适用场景（文本类项目可附试跑结果）
- 体现获客方法论：基于 W11 以来触达数据的渠道效果评估与调整策略

---

### 3.3 LLM分析实验（W13）

**基本规格**：
- 用 LLM 作为分析引擎完成至少1个分析实验（解读ML模型结果/LLM辅助特征探索/LLM从文档提取洞察，三选一）
- 说明 LLM 做数据分析 vs 传统 ML 建模的适用边界与互补（对照对象为 W11-W12 传统模型）

**知识锚定要求**：
- 体现大模型做数据分析：展示至少 1 个用 LLM 完成的分析/建模实验，并说明其相对于传统方法的优劣
- 体现神经网络基础认知：能说明神经网络的基本结构与训练原理（梯度下降的复用），并对自己的项目是否适合引入神经网络给出判断（进阶试跑 MLP 者附对比结果）

---

### 3.4 用户反馈记录 + 模型v1.0（W14）

**基本规格**：
- 反馈自 W11 部署成功后滚动触达收集（W12-W13 深化渠道），本周集中收口：向至少 5 位目标用户收集反馈（使用体验、功能需求、痛点），记录至少 5-10 条
- 多模型对比实验：从已学模型（线性/逻辑回归、朴素贝叶斯、SVM、决策树、随机森林）中选 ≥2 个适合自己问题类型的，在同一划分与同一指标下公平对比
- 结合用户反馈与对比结果调整模型方向，产出模型v1.0
- 兜底口径：真实用户不足时走互助测试池（`weeks/week13/user-test-pool.md`）/教师转介；确不足5位可以3位深度访谈替代——评估看深度不看数量；模型对比受阻时从简为"基础模型 vs 另一原理模型"两两对比

**知识锚定要求**：
- 体现获客方法论：通过什么渠道找到目标用户、推广策略是什么
- 体现用户反馈的分类与分析：区分"功能需求"和"体验问题"，并说明对模型/产品迭代的优先级影响
- 体现多模型对比方法：对比是否公平（同一划分/同一指标）、为什么最终选定该模型（对比结果与用户反馈各占什么权重）
- 体现据反馈迭代：用户反馈如何改变了模型方向或特征选择

### 3.5 产品v1.1（含模型+评估+文档+evals）+ 路演大纲与脚本（W15）

**基本规格**：
- 核心：评估模型（指标 MSE/R²/准确率/F1/混淆矩阵、交叉验证、偏差-方差）并嵌入产品；撰写使用文档
- 含 UX 优化与打磨
- 进阶(可选)：Agent 自动化、Skill 封装、AB 测试、深度评估
- 准备路演 PPT 大纲与 Demo 脚本（完整材料于 W16 课堂制作，本周只到大纲与脚本）
- 此处的模型与 AI 功能评估即项目工作流中的**反馈回路（feedback loop）**：为 AI 功能准备 10-20 条"问题—预期答案"作为 evals，写入 repo 作为回归测试（见 `teaching-plan.md` AI-Native 项目工作流节）

**知识锚定要求**：
- 体现模型评估与验证：不仅报分，而是说明指标含义、交叉验证如何避免过拟合、偏差-方差权衡
- 体现建模产品化：模型如何嵌入产品、训练→推理→展示架构
- 体现 AI 功能自检：说明测试了 AI 功能的哪些边界问题、发现什么不准/幻觉、如何修正提示或流程
- 体现 UX 优化的迭代逻辑：哪些体验问题被修复、修复依据是什么（用户反馈还是设计原则）
- 体现路演叙事方法论：故事线"问题→方案→产品(含模型)→价值"，Demo 聚焦核心价值环节而非功能罗列
